Different roles.
Different evidence.

The fieldwork changed the requirements discussion: a useful operating record and trusted monitoring evidence serve different jobs.

Research synthesis / redrawn for this case
Workers

Lower-text input

Graphical cues, scanning and photos as responses to observed input friction.

Managers

Useful operating records

Fit existing routines rather than require ideal, uninterrupted daily data.

Bank monitoring

Identity and data trust

Compare evidence needs and what remains when a monitoring link fails.

Input constraint

Reduce the writing burden.

I brought lower-text approaches into product discussions based on differences in language and confidence with written input.

Technical trade-off

Design for the blind spot.

A shared link can fail. Later analysis considered local collection plus GPS/BeiDou fallback by context, rather than one universal replacement.

Prototype scope

Keep the core flows connected.

I chose Flutter for the April MVP, prioritising cattle, alerts and weight entry with simulated data before relying on a production backend.

Checked in review

Turn “polish” into specific work.

Navigation visibility, alignment and consistency became concrete iteration items. The artefact made the direction inspectable.

Next evaluation

Return to the working context.

Test core tasks with the relevant roles in context and connect the hardware in the next evaluation.

This project connects field learning with a testable prototype: I conducted three days of research, contributed interface design and handoff, and used AI assistance to build an Android MVP with simulated data.
